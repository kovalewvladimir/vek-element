# Стенд профилирования VuVirtTable

Здесь лежит не тест, а инструмент. Он ничего не утверждает и ничего не охраняет — он печатает числа, по которым принимается решение «делать ли пункты 7–9 плана оптимизации». В обычный прогон `npx playwright test` не входит: без переменной `PERF` спека пропускается.

Регрессию оптимизаций держат тесты в [`../virt-table-optimization`](../virt-table-optimization), функциональность — [`../virt-table`](../virt-table).

## Из чего состоит

**Страница-стенд** `/vu-components/vu-virt-table/perf` — `apps/example/src/views/vu-components/vu-virt-table/table-perf.vue`. Самодостаточна: открывается в браузере, кнопки прогоняют сценарии, таблица результатов рисуется на самой странице. Playwright для неё не нужен.

**Спека профиля** `profile.spec.ts` — открывает ту же страницу, набирает данные, включает CDP-профилировщик, жмёт «Прогнать всё» и печатает разбивку по функциям. Нужна там, где кадров недостаточно: доля времени в реактивности видна только в профиле.

## Запуск

```sh
# страница вручную
npm run dev
# → http://localhost:8999/vu-components/vu-virt-table/perf?rows=50000&size=100

# профиль
PERF=1 npx playwright test virt-table-perf
PERF=1 PERF_ROWS=100000 PERF_SIZE=100 npx playwright test virt-table-perf
```

Параметры страницы: `?rows=` — размер набора, `?size=` — `sizePage`, `?summary=off` — выключить строку ИТОГО. Их же можно менять прямо на странице и нажать «Применить»: таблица пересоздаётся с нуля.

## Сценарии и что каким пунктом плана меряется

| Кнопка | Пункт | Что происходит |
| --- | --- | --- |
| Медленный скролл | 1, 5 | 2 px за кадр, 600 кадров — окно строк сдвигается примерно раз в 14 кадров |
| Быстрый скролл | 7 | 224 px за кадр, 200 кадров — окно сдвигается каждый кадр, `v-memo` промахивается на всех позициях |
| Клик по строке | 3 | 20 кликов: обход всех данных ради сброса `isActive` плюс перерисовка подсветки |
| Догрузка страницы | 2 | 10 append-ов по `sizePage` строк: мутация массива, пересчёт ИТОГО, инвалидация |
| Загрузить всё | — | настоящий бесконечный скролл до конца набора, до профилирования |

## Как читать метрики

Колонка **Метрика** говорит, что именно измерено, и это важнее самих чисел.

**`время кадра`** — интервал между двумя `requestAnimationFrame`. При 60 Гц он равен 16.7 мс, пока работа влезает в бюджет, поэтому **`p50` у скролла почти всегда упирается в vsync и сам по себе не значит ничего**. Смотреть надо на `max`, на «Пропущено» (кадры дольше 25 мс — порог намеренно выше бюджета, иначе джиттер вокруг vsync записал бы половину идеального прогона в просевшие) и на «Сверх бюджета» — сумму превышений, самый устойчивый показатель джанка.

**`время работы`** — реальная длительность синхронного обработчика вместе с перерисовкой (`await nextTick()` после действия). Здесь значима каждая колонка.

Разбивку по функциям кадрами получить нельзя — для неё снимается CPU-профиль.

## Оговорка про сборку

По умолчанию профилируется **dev-сборка**: Vue в dev-режиме, модули не собраны в бандл, подключён `vite-plugin-vue-devtools`. Внутренности Vue из-за этого заметно дороже, чем в проде, и доля рендера в профиле завышена. Для решения об архитектурном рефакторинге снимайте профиль с прод-сборки:

```sh
npm run preview -w vek-element-example -- --port 8999
# в другом терминале — playwright переиспользует уже поднятый сервер
PERF=1 npx playwright test virt-table-perf
```

## Данные детерминированы

Набор генерируется seeded-ГПСЧ (`mulberry32(1)`), поэтому прогон «до правки» и «после» идут на идентичных строках. Иначе часть разницы в замерах объяснялась бы разной длиной текста в ячейках, а не самой правкой.

Отсюда и правило сравнения: **числа этого стенда сопоставимы только с числами этого же стенда на той же машине**. Абсолютные значения зависят от железа и от того, что ещё крутится в системе; выводы делаются из отношения «до/после», а не из самой величины.
