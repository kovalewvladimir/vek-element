# Регрессия оптимизаций VuVirtTable

Тесты в этой папке существуют не для проверки функциональности таблицы — её покрывают спеки в [`../virt-table`](../virt-table). Здесь проверяется, что **оптимизации рендера не «залипли»**: не перестали обновляться те части таблицы, которые оптимизация намеренно перестала перерисовывать.

## Почему они отдельно

Обычный тест падает, когда сломана логика. Эти падают, когда логика цела, а на экране показано устаревшее. Такой дефект не воспроизводится ни в одном сценарии из `../virt-table` и почти не ловится код-ревью — поэтому вынесены отдельно и снабжены объяснением, что именно каждый из них держит.

## Что оптимизировано

В теле таблицы применены три приёма, которые сознательно сокращают реактивность:

1. **`v-memo` на строке** (`virt-table.vue`). Строка компилируется с patch-флагом `DYNAMIC_SLOTS`, из-за которого Vue не может пропустить её перерисовку при любом рендере родителя. `v-memo` возвращает закэшированный vnode и обрывает эту цепочку. Взамен строка обновляется **только** при изменении значений из списка зависимостей:

   ```
   v-memo="[row, getMetaData(row).isActive, computedVisibleColumns]"
   ```

   Забыть зависимость — значит получить строку, застрявшую на старых данных.

2. **Чтение сырых строк через `toRaw`** (`handleRowClick`, `findDataItemIndex`, `countItemsAtLevel` в `virt-table.vue`; `summaryRows` в `use-summary.ts`). Обход больших массивов идёт без создания Proxy на каждую строку. Правило: **читать можно из сырых объектов, писать — только через прокси**, иначе запись не разбудит рендер.

3. **Обработчики ячейки только в ветке заголовка** (`virt-table-row.vue`). Шаблон разделён на две ветки по `isHeader`: `@click`/`@contextmenu` рендерятся лишь для шапки, где на них висят сортировка и меню колонок. В теле и футере они эмитили в никуда — родитель подключает `<virt-table-row>` без этих слушателей, а клик по строке идёт через всплытие на `div.row`. Ячейка тела компилируется с patch-флагом `4 /* STYLE */` вместо `44 /* STYLE, PROPS, NEED_HYDRATION */` и не аллоцирует замыканий.

   Удалить обработчики совсем нельзя: корень компонента — фрагмент из `v-for`, fallthrough нативного `onClick` на ячейки не работает.

## Соответствие тестов и зависимостей

| Тест | Что держит |
| --- | --- |
| раскрытие и схлопывание узла дерева | `countItemsAtLevel` на сырых строках, `invalidateVirtualData` после splice, `hasNestedRows` |
| Tree Disable убирает стрелки, Enable возвращает | `treeComputed.enabled` в зависимости `v-memo` **не входит** — дочерний компонент обязан обновляться сам |
| кнопка Изменить перерисовывает первую строку | зависимость `row`: `updateDataItem` подставляет новый объект с тем же `id`, key-guard `v-memo` его не различает |
| клик по строке переносит подсветку | зависимость `getMetaData(row).isActive` плюс правило «писать через прокси» в `handleRowClick` |
| клик по заголовку сортирует колонку | обработчики `@click`/`@contextmenu` в ветке `isHeader` компонента `virt-table-row` |
| скрытие колонки через меню применяется к строкам | зависимость `computedVisibleColumns`: при memo-hit дочерний `virt-table-row` не получит новый массив колонок |

## Проверено мутационно

Набор не «на всякий случай» — каждая зависимость `v-memo` проверена удалением:

| Убрать из `v-memo`          | Падает                                           |
| --------------------------- | ------------------------------------------------ |
| `row`                       | кнопка Изменить перерисовывает первую строку     |
| `getMetaData(row).isActive` | клик по строке переносит подсветку               |
| `computedVisibleColumns`    | скрытие колонки через меню применяется к строкам |

Убрать все три (`v-memo="[row]"` и уже) — падают два теста из трёх соответствующих. Обратное тоже проверено: `treeComputed.enabled` в зависимостях не нужен, тест Tree Disable/Enable проходит без него 5 прогонов из 5.

Разделение веток в `virt-table-row.vue` проверено так же:

| Сломать | Падает |
| --- | --- |
| убрать `@click` из ветки `isHeader` | клик по заголовку сортирует колонку — ровно один тест, остальные 5 проходят |

Обратной проверки у этого приёма нет и быть не может: лишние обработчики на ячейках тела снаружи ничем не наблюдаются, это свойство производительности. Единственное доказательство — скомпилированная render-функция, поэтому patch-флаг ветки тела указан выше явно.

Если добавляете новую оптимизацию рендера в таблицу — повторите этот приём: сломайте её намеренно и убедитесь, что тест это видит.

## Запуск

```sh
npx playwright test virt-table-optimization
```
